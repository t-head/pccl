基线为 1d5f6eee10addeaea6d27b257c770a59ddf9bad0，原 CBD 分支 perf/coll-fc-tree-cbd。本次提交到独立分支 perf/cbd-collective-sort，关联 runtime 跟踪 issue #152。

  1. 第一笔：排序＋聚合调优及回归测试。提交 b8243b533f572466b4b7264883d82c00c3ece9ec。先按近似通信量排序，再按 collective / device reduction op / datatype 分组，组合相近大小任务进行调优。重排发生在注册和对应 work/cleanup 队列建立之前。加入混合类型、root、用户归约操作、注册缓冲区及小预算测试与 CI 接线。这笔中间提交存在本文记录的性能回退，应连同第二笔使用。
  2. 第二笔：恢复逐任务调优。即本文件所在提交。保留执行队列排序，删除累计 count / nBytes 后共用策略的逻辑；对排序后的每个原始任务单独调用 getAlgoInfo，恢复原 CBD tuner 插件输入。算法、协议、通道数、线程数均按任务本身确定。没有修改 device kernel 或重新调整整套性能模型。

1.1 Patch 详细说明：从 API 任务到执行队列

阅读入口：第一笔完整提交与分支最终 enqueue.cc。下面分别解释第一笔引入的机制，以及第二笔保留、撤回的部分；文末可展开两笔代码 diff。第二笔的文档本身不递归包含在 diff 中。

A. 修改落在哪里，什么时候执行

API 提交 → collTaskAppend：保存原始任务及 opDev 快照
          → ncclPrepareTasks
              ├─ symmetric 路径先提取可处理任务
              ├─ 没有普通 collective：返回
              ├─ 一个 collective 且无 P2P：保留原单任务/外部 kernel 分支
              └─ 普通多任务路径：ncclSortAndTuneCollTasks
                    → 重排 collTaskQueue
                    → 最终版逐任务 getAlgoInfo
                    → 设置所需算法连接标志
          → 后续注册、work/cleanup 队列构建、plan 划分和执行

改动直接重建 planner 的 collTaskQueue，因此改变的是后续真正消费的任务顺序，而不只是调优遍历顺序。重排必须在注册创建配套 work/cleanup 队列之前完成，避免任务链表与这些配套队列错位。任务数量、用户缓冲区、原始 count、root 和归约参数没有被合并或重写。该路径不重排 P2P 队列，也不新增外部 kernel 的 grouped 支持。

B. 第一笔：通信量近似排序和 (fn, op, type) 分组

  1. 计算排序权重。ncclTaskCollTrafficBytes 对 AllReduce 取饱和的两倍 nBytes：nBytes + min(nBytes, SIZE_MAX - nBytes)；其他 collective 直接使用 nBytes。AllGather/ReduceScatter 的该字段已包含 rank 倍率，不能再次乘 ranks。权重用于粗略比较通信量，不是测得的网络字节数，也不会替换任务自身的调优大小。
  2. 分入大小桶。使用 unitLog2=10、maxLog2=30、bitsPerPow2=2，共 81 个固定桶。排序输入先截到 1 GiB，再右移 10 位，交给 u32fpEncode 编码；两个有效分档位提供近似大小等级。小于 1 KiB 的输入落入零档，超过上限的输入落入顶部档位。截断只影响排序键，不截断实际消息。这里不是按精确字节数做全排序。
  3. 再按类型组合成桶。ncclTaskCollFnOpTy 将 func、opDev.op、datatype 编为整数索引。遍历大小桶时从大到小扫描，记录各类型桶第一次出现的次序；任务再以头插法放入类型桶，使每个类型桶内部按近似大小递增。
  4. 恢复实际执行链表。按记录的类型桶次序重新入队。两次头插使同一大小桶、同一类型组合内的任务保留提交顺序；不同大小桶或不同类型组合之间允许重排。最终结果是“类型桶按首次遇到顺序排列、桶内近似升序”，并非整个 group 全局升序。

例如只考虑 AllReduce 和 Broadcast，原始序列为 AR 64 KiB → Bcast 8 KiB → AR 4 KiB，权重分别为 128、8、8 KiB。先遇到的较大 AR 确定 AR 类型桶在前，桶内恢复升序后形成 AR 4 KiB → AR 64 KiB → Bcast 8 KiB。这个例子只说明队列顺序，不表示三个任务会融合成一次 collective。

排序阶段复用原任务的 next 指针，使用固定大小栈数组，不新建任务、不为每个任务分配堆对象。遍历代价随任务数线性增长，另有固定桶扫描开销。排序可能改善同类型任务的调度局部性；具体收益以本文混合用例实测为准，不能仅凭排序推断 kernel 数量减少。

C. 正确性约束：哪些字段可以排序，哪些必须留在任务上

约束实现选择与原因
所有 rank 产生相同次序使用一致的 collective 元数据；不以本地缓冲区地址、用户 op 句柄或 scalar 值作为键。
用户归约操作以设备操作类别 opDev.op 分桶；scalarArg/scalarArgIsPtr 随原任务快照保留，允许各 rank 的 PreMulSum scalar 不同。
root 和消息大小root、count、nBytes 留在原任务；同一类型桶允许不同 root 和 count，不把分桶视为语义合并。
异常路径能找到任务在任何可能失败的 getAlgoInfo 调用之前，先把所有任务重新发布到完整 collTaskQueue。
注册与资源清理顺序重排在配套 work/cleanup 队列建立之前；后续阶段统一消费重排后的同一条任务链。
原 API 调用归属出队时保存排序前最后一个普通 collective；调优结束后恢复 comm->collType 和 comm->nBytes。
模拟估时setCollSimInfo 用最后提交任务的原 nBytes 和最终策略计算 estimatedTime；不是所有任务耗时求和。

上述一致性依赖各 rank 按 collective 契约提交匹配的元数据。排序也不能为任意缓冲区重叠或跨任务数据依赖提供正确性保证；新增测试使用独立缓冲区，未验证重叠缓冲区和图重放。队列完整性设计避免“调优失败后任务丢在局部桶里”，但不等价于对全部错误恢复路径做过故障注入。

setCollSimInfo 从既有调优函数提取：单 rank 返回 0；正常情况调用 ncclTopoGetAlgoTime，查询失败或估时为负时回退到 0。保存 last 是为了防止排序后的尾任务覆盖原来“最后提交 collective”的估时语义。

D. 第一笔中后来撤回的部分：相近任务聚合调优

第一笔在排序后复制首任务到栈上 aggregate，沿同一 (fn, op, type) 连续段累加 count 和 nBytes。下一任务必须满足 nextTraffic / 4 < firstTraffic，等价于正整数大小下的 nextTraffic < 4 × firstTraffic，并且两项求和均不溢出 SIZE_MAX。这里用除法避免比较式乘四溢出；比较基准始终是段首任务，不是上一个任务。

对累计任务调用一次 getAlgoInfo 后，把 algorithm、protocol、nChannels、nThreads 四个字段回写给段内各原任务。同时把 tuner 调用的原始零值参数替换为 DIVUP(planner->nTasksColl, comm->nChannels)。累计对象只用于选策略，实际任务仍保持各自缓冲区和大小，因此可能出现本文的 64 KiB → 320 KiB 策略跨阈值问题。

2. 哪些参考 NCCL，哪些是 PCCL 的选择

主要参考版本为 NCCL v2.27.3-1，提交 72d2432094d6ae36abd6e511c3a16a2d052dbf94。其 任务分组和聚合调优源码明确将相近大小任务聚合、调用调优，再将策略写回各任务。

  • 排序：参考 NCCL 的近似通信量排序与 (fn, op, type) 分组；PCCL 保留自身可用的调度路径，不引入 CollNet/NVLS 分桶。
  • 初版聚合调优：同样参考 NCCL，对大小相近的任务进行累计调优；这是带来本次回退的迁移部分。
  • 最终逐任务调优：针对当前 PCCL 模型和设备路径的实测适配，恢复原 CBD 行为。它不是从 NCCL 移植来的“修复补丁”，最终实现也不是完整照搬 NCCL。

不能由本次结果推断 NCCL 自身的聚合调优有问题，也没有证明逐任务调优在所有 PCCL 拓扑、协议和未来版本上都最优。若将来重新引入聚合调优，需要将任务数量、执行分布、协议阈值与调度模型一起验证。
